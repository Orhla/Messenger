## Сначала — фикс из домашки 5

Перед тем как двигаться дальше, исправь баг в `fetchMessages`: запрос тянет все сообщения где собеседник — отправитель ИЛИ получатель, включая его переписку с другими пользователями. Нужно фильтровать только переписку между двумя конкретными пользователями:

```ts
// было — неправильно, тянет чужие диалоги
.or(`sender_id.eq.${correspondentId},receiver_id.eq.${correspondentId}`)

// стало
.or(
  `and(sender_id.eq.${correspondentId},receiver_id.eq.${currentUserId}),` +
  `and(sender_id.eq.${currentUserId},receiver_id.eq.${correspondentId})`
)
```

Также в `subscribeToMessages` — если сообщение не расшифровалось, `onMessage` не вызывается совсем и сообщение просто исчезает. Нужно вызывать `onMessage` с текстом-заглушкой по аналогии с тем, как это сделано в `fetchMessages`.

## Блок А — Миграции

Три новые таблицы. Для каждой подумай: какие поля нужны, какие из них `not null`, какие внешние ключи.

### А1 — `rooms`

Комната знает своё название и кто её создал. Посмотри как устроена таблица `profiles` — структура похожая.

### А2 — `room_members`

Связь многие-ко-многим между комнатами и пользователями. Подсказка: вместо отдельного `id`-поля попробуй сделать `primary key (room_id, user_id)` — это сразу и уникальность гарантирует, и индекс создаёт.

### А3 — `room_messages`

**Почему отдельная таблица, а не добавить `room_id` в `messages`:**
Таблица `messages` заточена под 1:1 — там есть `sender_id` и `receiver_id`. У группового сообщения нет `receiver_id`. Если добавить `room_id` и сделать `receiver_id` nullable, получится "полиморфная" таблица: в каждом запросе нужно проверять, какого типа строка, RLS становится запутанным, индексы общие для разной семантики. Две отдельные таблицы — два чётких контракта.

### А4 — RLS

Для каждой таблицы сформулируй правила словами, потом переводи в SQL:

- `rooms` — читать могут только те, кто состоит в комнате; создавать может любой авторизованный
- `room_members` — читать и добавлять новых участников могут только существующие участники комнаты
- `room_messages` — читать и писать могут только участники комнаты; при вставке `sender_id` должен совпадать с текущим пользователем

Посмотри на RLS из предыдущих домашек — паттерн с `exists (select 1 from ...)` тебе уже знаком.

**Проверка:** таблицы появились в Supabase Studio. Попробуй из SQL-редактора вставить участника в комнату в которой ты не состоишь — должна вернуться ошибка RLS.

## Блок Б — API

Создай `src/lib/rooms.ts` и добавь нужные типы в `types.ts`. Нужны следующие функции:

- `createRoom(name)` — создаёт комнату и сразу добавляет создателя как первого участника (два insert'а)
- `getRooms()` — список комнат текущего пользователя (RLS сам отфильтрует лишнее)
- `addMember(roomId, userId)`
- `getRoomMembers(roomId)` — список профилей участников. Подсказка: Supabase умеет делать join через `.select('profiles(*)')` — посмотри как это работает
- `fetchRoomMessages(roomId)` — при выборке сообщений сразу подтяни email отправителя через `.select('*, profiles(email)')`, чтобы не делать отдельный запрос в UI
- `sendRoomMessage(roomId, text)`
- `subscribeToRoomMessages(roomId, onMessage)` — возвращает функцию отписки, как в `messages.ts`. Важно: при подписке на realtime укажи фильтр `room_id=eq.${roomId}` на уровне канала — без этого придут события из всех комнат

**Проверка:** в консоли вручную вызови `createRoom`, `getRooms`, `sendRoomMessage`, `fetchRoomMessages` — убедись что данные появляются и RLS не блокирует.

## Что важно не забыть

- `addMember` может вернуть ошибку если пользователь уже в комнате (primary key violation) — обрабатывай явно, показывай понятный текст ("Пользователь уже в комнате").
- Если список комнат пустой — покажи подсказку "Создайте первую комнату", не пустой экран.
- Realtime-подписка на комнату должна отписываться при смене активного чата (так же как сделано для 1:1 через `useEffect` cleanup).
- `getRoomMembers` делает запрос при каждом открытии панели участников — это нормально, кешировать не нужно.
