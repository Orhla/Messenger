# Домашнее задание 7 — Рефакторинг чата

Новых фич нет. Цель: то же поведение, но код, который удобно читать и менять. Делаем маленькими шагами, после каждого шага приложение должно работать.

---

## Решение, которое мы приняли

На уроке разбирали PR #5 и сравнивали два пути разгрузки `Chat.tsx` (~280 строк):

- **А. Компоненты + пропсы + стейт** — разные режимы чата живут в разных компонентах.
- **Б. Кастомные хуки** — логика переезжает в хуки, компонент остаётся склейкой.

**Выбираем А.** Причины:

1. Главная проблема `Chat` — он обслуживает два режима (direct и room) и ветвится по `kind` в пяти местах: загрузка, подписка, отправка, заголовок, рендер. Хук ветвление не убирает, а переносит внутрь.
2. Хук, который используется в одном компоненте, сейчас только добавляет строки. Пример из PR: `useRoomMembers(roomId: string | null)` — `null` существует лишь потому, что `Chat` знает про оба режима.
3. Поток данных сверху вниз через пропсы проще читать и объяснять.

4. Тестов в проекте нет, поэтому главная выгода хуков (изолированное тестирование) не работает. Переиспользования тоже нет: каждый хук использовался бы ровно в одном месте.

**Поэтому `useRoomMembers` (из PR #5) удаляем**, а загрузку и добавление участников делаем прямо внутри `RoomChat` через `useState` + `useEffect`. Все эффекты и обработчики чата вызываются внутри самого компонента, новых кастомных хуков не вводим.

**Хуки не запрещены навсегда.** Если когда-нибудь появятся тесты или реальное переиспользование (один и тот же код нужен в двух разных экранах), вернёмся к вопросу. Решаем по факту, а не заранее.

## Блок 1 — Разбиваем `Chat` на компоненты

Было: один `Chat.tsx`, который загружает данные, подписывается, отправляет, управляет участниками, навигацией и рисует всё сразу.
Стало: каждый компонент отвечает за одну вещь.

### Целевая структура

```
ChatLayout            ← Sidebar + область справа (Outlet / children)
├─ Sidebar            ← уже есть, получает activeRoomId из URL
└─ main
   ├─ ChatPlaceholder ← /chat без выбранного чата
   ├─ DirectChat      ← /chat/direct/:chatId
   │   └─ ChatView
   └─ RoomChat        ← /chat/room/:chatId
       ├─ ChatView
       └─ MembersPanel
```

### Что должен делать каждый компонент

| Компонент | Ответственность | Пропсы |
|---|---|---|
| `ChatLayout` | Рисует `Sidebar` и область справа. Не знает ничего про сообщения | `children` |
| `ChatPlaceholder` | Экран «Выберите, кому написать, или войдите в комнату» | — |
| `EmptyState` | Универсальная заглушка: иконка/заголовок/описание + `children`. Заменяет три копии из `Chat.tsx` (загрузка, ошибка, «не найден») | `title`, `description?`, `tone?`, `children?` |
| `ChatView` | **Презентационный.** Шапка + `ChatArea` + `ChatFooter`. Владеет только текстом в поле ввода. Не знает про Supabase и про тип чата | `header`, `messages`, `onSend(text)` |
| `DirectChat` | Загружает профиль собеседника, сообщения, подписывается на новые, отправляет. Рендерит `ChatView` | `chatId` |
| `RoomChat` | То же для комнаты: комната, участники, сообщения, подписка, отправка, добавление участника. Рендерит `ChatView` | `chatId` |
| `ChatHeader` | Только название, подзаголовок и кнопка выхода. Дополнительные действия приходят через `children` | `title`, `subtitle?`, `children?` |
| `MembersPanel` | Список участников + поиск для добавления. Вынести из `ChatHeader` | `members`, `onAddMember` |

### Шаги

1. **`EmptyState`.** Вынеси из `Chat.tsx` три одинаковые заглушки (загрузка, ошибка, «не найден») в один компонент. Замени ими блоки в `Chat`. Проверка: внешне ничего не изменилось.
2. **`MembersPanel`.** Вынеси панель участников из `ChatHeader` (~40 строк). `ChatHeader` теперь принимает `children` и больше не знает про `kind` и `members`.
3. **`ChatView`.** Собери из `ChatHeader` + `ChatArea` + `ChatFooter`. Состояние `text` и `onKeyDown` живут внутри; наружу — только `onSend(text)`.
4. **`DirectChat`.** Перенеси из `Chat` всё, что касается direct: загрузка профиля, сообщения, подписка, отправка. Внутри ни одного `if (kind === 'room')`.
5. **`RoomChat`.** То же для комнаты (+ участники и `MembersPanel`). Участников грузи и добавляй прямо в компоненте (`useState` + `useEffect`), хук `src/hooks/useRoomMembers.ts` удали вместе с папкой. `chatId` приходит обычной строкой, без `null`. В эффекте оставь флаг `cancelled` в cleanup, чтобы запоздалый ответ от прошлой комнаты не перезаписал текущую.
6. **`ChatLayout` и роуты.** Обнови `App.tsx`: `/chat` → `ChatPlaceholder`, `/chat/direct/:chatId` → `DirectChat`, `/chat/room/:chatId` → `RoomChat`, всё внутри `ChatLayout`. `Sidebar` определяет активную комнату по `useParams`, а не по `ActiveChat`.
7. **Проверка id на роуте.** Вместо трёх проверок `isUUID` внутри компонента сделай маленький `ValidChatId` рядом с `ProtectedRoute`: берёт `chatId` из `useParams`, при невалидном показывает `EmptyState`, иначе отдаёт `chatId: string` дочернему компоненту.
8. **Удали `Chat.tsx`.** Заодно удали мёртвый код: `SelectChat.tsx` и `ui/dialog.tsx`.

### Чек-лист готовности

- [ ] Поведение приложения не изменилось (создать комнату, добавить участника, написать в direct и в комнату, перезагрузить страницу)
- [ ] `Chat.tsx` удалён, ни один новый файл не длиннее ~120 строк
- [ ] Нигде нет ветвления `kind === 'room' | 'direct'`; компоненты `DirectChat` и `RoomChat` не знают друг о друге
- [ ] `ChatView` не импортирует ничего из `@/lib/*`
- [ ] `isUUID` вызывается в одном месте
- [ ] Папки `src/hooks` нет: вся логика загрузки, подписок и отправки живёт внутри компонентов
- [ ] `npx tsc -b` проходит

### Подсказки

- Начинай с шага 1: он самый простой и даёт сразу видимый результат.
- Если после разделения `DirectChat` и `RoomChat` выглядят похоже, это нормально. Хук не вводим. Для дедупликатора `prev.some(...)` достаточно маленькой чистой функции `appendUnique(list, item)` (обычная функция, не хук).
- Если какой-то компонент хочется назвать «Manager», «Handler» или «Container», скорее всего, он делает больше одной вещи.
- Не добавляй функциональность по ходу рефакторинга. Баги, которые найдёшь, записывай отдельным списком.

## Блок 2 — `SearchUsers`: нейтральный компонент

Сейчас `SearchUsers` вставлен в 7 мест, и каждое приходится оборачивать в свой div: внутри зашит контейнер `p-3 border-b bg-muted/30 relative z-10`. Задача: компонент делает одну вещь (ищет и отдаёт выбранного), а где он стоит и как выглядит, решает вызывающий.

### Что должно получиться

| Проп | Назначение |
|---|---|
| `onSelect(profile)` | вместо `onSelectReceiver` (компонент не знает, получатель это или участник комнаты) |
| `excludeIds?: string[]` | кого не показывать в результатах: себя, уже добавленных участников |
| `placeholder?` | по умолчанию «Найти пользователя...» |
| `className?` | стили контейнера снаружи |

### Шаги

1. **Убери из `SearchUsers` стили контейнера** (`p-3 border-b bg-muted/30`), оставь только то, что нужно самому компоненту (`relative` для выпадающего списка). Внешний вид возвращай снаружи через `className`.
2. **Добавь `excludeIds`.** Профили из этого списка не попадают в выпадающий список. Используй в `MembersPanel` (исключи текущих участников) и в `NewRoom` (исключи уже выбранных и себя).
3. **Debounce без хука.** Запрос не на каждую букву, а через ~300 мс после остановки ввода: `setTimeout` внутри `useEffect` и `clearTimeout` в cleanup.
4. **Защита от гонки и ошибок.** В том же эффекте флаг `cancelled`: ответ на старый запрос не должен перезаписать свежий. Добавь `.catch`, чтобы ошибка поиска не превращалась в unhandled rejection (показывай пустой список).
5. **Замени все вставки** (`Sidebar`, `MembersPanel`, `NewRoom`, `ChatPlaceholder`, заглушки) на новый API. Лишние обёртки удали.

### Чек-лист

- [ ] В `SearchUsers` нет `border`, `bg-*` и внешних отступов
- [ ] Нельзя добавить в комнату себя или уже добавленного участника
- [ ] При быстром вводе уходит один запрос, а не по запросу на символ
- [ ] Нигде не осталось лишних обёрток вокруг `SearchUsers` ради границ и фона

## Блок 3 — Слой данных: одна модель и два файла

Сейчас типы БД протекают прямо в UI: `ChatArea` делает `'profiles' in m`, а `GroupChatMessage.profiles` объявлен обязательным, хотя в realtime-payload его нет, то есть тип врёт (это причина UUID вместо email у новых сообщений в комнате). Задача: UI работает с одной моделью сообщения и ничего не знает про форму таблиц.

### Единая модель

```ts
// то, что видит UI
export type Message = {
    id: string;
    senderId: string;
    senderLabel: string; // email отправителя, а не UUID
    text: string;
    createdAt: string;
};
```

`ChatMessage`, `GroupChatMessage` и проверки `'profiles' in m` из компонентов уходят совсем. `ChatArea`, `ChatView`, `DirectChat`, `RoomChat` работают только с `Message`.

### Разделяем `lib` на два слоя

```
src/lib/
├─ api/           ← только Supabase: запрос → «сырая» строка БД. Никакой логики
│   ├─ messages.ts       (direct: select / insert / realtime)
│   ├─ roomMessages.ts
│   ├─ rooms.ts
│   └─ profiles.ts
├─ mappers.ts     ← чистые функции: сырая строка → модель UI. Без Supabase, без React
└─ types.ts       ← DbMessageRow, DbRoomMessageRow (как в БД) и Message, Profile, Room (для UI)
```

Правило: **`api/*` знает про Supabase, `mappers.ts` знает про формы данных, компоненты знают только про модель UI.** Зависимости идут в одну сторону: компонент → api → mappers (или компонент → mappers).

### Что делают мапперы

```ts
// расшифровку делает messages.ts в слое api (она асинхронная), в маппер приходит готовый text
toDirectMessage(row: DbMessageRow, text: string, correspondent: Profile): Message
toRoomMessage(row: DbRoomMessageRow, members: Profile[]): Message
```

`toRoomMessage` берёт email так: сначала `members.find(...)` (список участников уже есть в `RoomChat`), потом `row.profiles?.email` (если пришёл join), иначе строка «Неизвестный пользователь». Благодаря этому у сообщений из realtime тоже будет email, а не UUID.

### Шаги

1. **Типы.** В `types.ts` опиши `DbMessageRow`, `DbRoomMessageRow` (как в таблицах, `profiles` у room-сообщений необязателен) и `Message`.
2. **`mappers.ts`.** Напиши `toDirectMessage` и `toRoomMessage`. Это обычные функции без побочных эффектов, их можно проверить в консоли на трёх строчках данных.
3. **Перенеси запросы в `lib/api/`** (просто переместить и поправить импорты). `fetchMessages`, `fetchRoomMessages` возвращают сырые строки, маппинг делает вызывающий (`DirectChat`, `RoomChat`).
4. **Типизируй ответы Supabase** и убери `any` из `getRoomMembers` (`item: any`, `Array.isArray`, `filter(Boolean) as Profile[]`). Подскажет генерация типов или явный тип строки запроса.
5. **`getRoomById(id)`** вместо `getRooms().then(rooms.find(...))` в `RoomChat`. Один запрос на одну комнату.
6. **`createRoom` без `getSession`.** Принимай `creatorId: string` и `memberIds: string[]` аргументами (не `Profile[]`). Слой `api` не должен лезть в авторизацию, id текущего пользователя вызывающий возьмёт из `useAuth()`.
7. **`ChatArea` и `ChatView` принимают `Message[]`.** Удали `'profiles' in m`, подпись берётся из `m.senderLabel`.

### Чек-лист

- [ ] В компонентах нет импортов `ChatMessage` и `GroupChatMessage`, нет `'profiles' in m`
- [ ] В `lib/api/*` нет логики отображения, в `mappers.ts` нет `supabase`
- [ ] Нет `any` и `as Profile[]` в слое данных
- [ ] В комнате у новых realtime-сообщений от других отображается email, а не UUID (проверь в двух вкладках)
- [ ] `createRoom` не импортирует `@/lib/auth`
- [ ] `npx tsc -b` проходит

### Подсказки

- Сначала напиши типы и мапперы, потом переноси запросы. Так компилятор подскажет все места, где UI ещё ждёт старые типы.
- Если маппинг хочется положить в компонент «на минутку», остановись: через неделю таких мест будет пять.
